Case Study

Library Management System

A full-stack library system built from the ground up with core Java technologies — no framework shortcuts — to deeply understand authentication, database access, and server-side architecture before moving to Spring Boot.

Role
Solo Developer
Duration
Personal Project
Stack
Java · React · MySQL
01

The Problem

Most beginner Java projects stop at console-based CRUD apps. I wanted to build something closer to a real deployed system: a web app with actual user accounts, permission levels, a persistent database, and business logic that has to handle edge cases — like what happens when a book is returned late, or when a member tries to borrow a book that's already checked out.

The goal was a Library Management System that a real library could plausibly use: admins manage the catalog and members, while members browse, borrow, and return books — with the system automatically tracking due dates and overdue status.

02

Architecture

The backend is built on raw Java Servlets talking directly to MySQL through JDBC — deliberately avoiding Spring at this stage so every layer of the request lifecycle (routing, session handling, SQL, response serialization) had to be understood and wired by hand.

┌─────────────┐ HTTP/JSON ┌──────────────────┐ │ React SPA │ ──────────────────────▶ │ Servlet Layer │ │ (Vite) │ ◀────────────────────── │ (Controllers) │ └─────────────┘ └────────┬─────────┘ │ ┌────────▼─────────┐ │ Service Layer │ │ (business logic: │ │ borrow/return, │ │ overdue calc) │ └────────┬─────────┘ │ ┌────────▼─────────┐ │ JDBC + DAO │ └────────┬─────────┘ │ ┌────────▼─────────┐ │ MySQL DB │ └──────────────────┘ Session Auth ──▶ stored server-side, validated per-request BCrypt ──▶ password hashing before persisting to DB Gson ──▶ Java objects ⇄ JSON serialization

Deployed locally on Apache Tomcat, built and dependency-managed with Maven. The frontend is a separate React + Vite single-page app that consumes the servlet API over HTTP.

03

Key Features

  • Role-based access control — distinct Admin and Member views and permissions
  • Session-based authentication with BCrypt-hashed passwords
  • Book CRUD — add, edit, remove, and search catalog entries
  • Borrow/return workflow with availability checks
  • Automated overdue tracking based on due dates
  • Admin dashboard for managing members and monitoring activity
  • Dark, Spotify/Netflix-inspired UI for a polished user experience
04

Challenges & Fixes

Building without a framework meant hitting — and solving — problems Spring normally hides:

Session handling across requests
Without Spring Security, session state had to be manually validated on every protected servlet endpoint. Fix: a shared filter/check at the start of each servlet method to verify session validity before executing logic.
Preventing double-borrowing of the same book
Two members could try to borrow the last copy at nearly the same time. Fix: availability check moved into the same transaction as the borrow insert, so the DB itself enforces the constraint rather than the UI.
Password security
Storing plain-text passwords is a non-starter. Fix: BCrypt hashing on signup, with hash comparison (not plain equality) on login.
Manual JSON serialization boilerplate
Every servlet response needed consistent JSON output. Fix: standardized on Gson across all endpoints to keep request/response shape predictable for the React frontend.
Overdue calculation edge cases
Naive date subtraction broke on same-day returns and timezone differences. Fix: normalized all date handling server-side before calculating overdue days.

06

What This Project Taught Me

Building the auth, session handling, and JSON layer by hand — instead of starting with Spring Boot — made the "magic" behind frameworks make sense. Now that I'm learning Spring Boot, I already understand what problems it's actually solving under the hood: request routing, dependency wiring, security filters, and ORM — rather than treating them as black boxes to memorize.
